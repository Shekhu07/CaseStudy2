# Prototype usability survey — 15 required questions + 2 optional, ~4 minutes

Generated by `create-prototype-usability-form.gs`. Paste that into
<https://script.google.com> and run `createPrototypeUsabilityForm`; this file
is the rationale behind it.

## What it is for, and what it is not

This is **not** the `wishlist-survey.md` instrument. That one asks about a
respondent's *real* Myntra wishlist and feeds Part 2/Part 4. This one asks
about **five minutes spent on the live reconnection prototype** —
`wishlist-reconnection-prototype.vercel.app` — using its fixed demo catalog
and its 30-item seeded wishlist, and it feeds the **usability half** of
Part 6/7: the questions `panel-sizing.md` already found a 300–500-person panel
*can* answer, because they don't need a 30-day cohort —

> Do participants understand why the module appeared? (§4 target: ≥80%)
> Can they recover from an unavailable variant?
> Do the states read correctly?
> Is the Buy/Compare split driven by the button fills? (§4.4)

— plus the two questions this round was actually asked for: **can someone
find what they'd saved**, and **is what they get told good enough to act on**.

It does not replace telemetry. Click-through, which button fires first, and
actual recovery behaviour are all logged by the harness already
(`analytics/events.ts` in the prototype repo) and are the authoritative
signal. This form exists for the thing telemetry cannot see: whether the
person understood *why*, and whether they'd trust it enough to stop looking
elsewhere — comprehension and confidence are self-report by nature.

## Before someone fills this in

They need to have just used the prototype, not be describing it from memory.
The form's own first page carries the task list — no separate moderator
script — because this is meant to run unmoderated, at panel scale, not as a
6-person interview. (**The 6 walkthroughs are a different instrument** —
`interview-guide.md` — and probe the person's *real* wishlist, before this
prototype existed for them to react to.)

Suggested search terms are given rather than left open, because the demo
catalog is small and specific: `shirt`, `jeans`, `kurta`, `handbag` are
documented in the prototype's own README to resolve to saved items and
produce a complete look (men's shirt → jeans → belt → watch; women's kurta →
handbag → flats → earrings → belt). An unguided respondent typing an
unrelated term would see nothing and rate a working feature as broken.

## The questions

| # | Measures | Feeds |
|---|---|---|
| 2 | which tasks were actually completed | frames every later answer — an unattempted task's questions have a safe "didn't do this" out rather than forcing a guess |
| 3 | task success — found a saved item while searching | the plain question this survey exists to answer, and the numerator under L1 (Reconnection view rate, Part 6 §6.3) |
| 4 | comprehension — *why* it appeared | panel-sizing.md's own ≥80% target; this is the number that goes in that cell |
| 5 | what was confusing, if anything | free text, only useful when Q4 isn't "clearly" |
| 6 | decision confidence, self-reported | proxy for L2 doubt-resolution (Part 6) — a number telemetry alone can't produce, because "added to cart" and "resolved and decided not to buy" both look like a terminal state in the logs |
| 7 | good enough to decide, vs. still needs elsewhere | the sharpest test in the set — "helped, but I'd still check elsewhere" is a partial failure of L2 even if Q6 scored high |
| 8 | what's still missing, in their own words | the same test `wishlist-survey.md` Q9 runs on the *idea* of a fix, now run on the *actual* one: if the answer names something the screen already showed, they missed it (a UI problem); if it names something the screen genuinely doesn't say, we built a message |
| 9 | recovery from an unavailable variant | panel-sizing.md's named usability question, direct |
| 10 | does the action feel like a decision or a toast | the exact distinction Improvement 3 in the prototype's own README claims to have fixed — this is the test of whether it worked |
| 11 | which action was noticed/tapped first, and why | self-report companion to the §4.4 swapped-fill click telemetry — treat disagreement between this answer and the logged click as a finding, not an error |
| 12 | did reordering the comparison help or just reshuffle | Compare screen's whole thesis (priority reorders, never hides) |
| 13 | was a pairing suggestion useful | cross-category pairing, kept provisional pending interview evidence (STATUS.md) — this is the panel-scale half of that evidence |
| 14 | the CS1 test, asked straight | "did this feel like a reminder, or different" — a treatment that reads as a notification with better copy has failed regardless of every other answer |
| 15 | one open ask | the softest signal on the form; read it, don't build from it alone |

Q16–17 (age, city) are optional and describe the sample only, same convention
as `wishlist-survey.md`.

## Design choices carried over from the wishlist survey, and one dropped

**Time anchors and named subjects, not vague adverbs.** Every question names
"that item" or "that module" outright, for the same reason as before — no
pronoun should depend on a page heading.

**No branching.** `wishlist-survey.md`'s branches exist because an empty
wishlist genuinely has nothing to answer about. Nothing here is like that:
every respondent used the same seeded demo, so instead of branching, any
task-specific question carries a **"didn't do this" / "didn't run into this"**
option and stays on the main path. This is a deliberate simplification —
`update-form-runbook.md` already documents branching as the API's most
fragile corner, and a shorter, unmoderated, at-panel-scale form is exactly
where a silently broken branch would cost the most responses before anyone
noticed.

**No "would this be useful to you?" hypothetical.** Same rule as the wishlist
survey, for the same reason, but it lands differently here: the respondent
just *used* the thing, so every question can be asked in the past tense about
what actually happened, which is a stronger instrument than the discovery
survey had access to.

## What this cannot tell you

- **It is not the 30-day cohort metric.** Nothing here substitutes for W30 or
  for a real production ramp; see `panel-sizing.md` for exactly what a
  300–500 panel can and cannot power.
- **Self-reported confidence (Q6) is not the same as a correct decision.** A
  respondent can feel confident and still be wrong about fit — this form
  measures *felt* doubt-resolution, and G3 (size-recommendation kept-rate, if
  the module ever emits one) is the number that would catch the difference.
- **Q11 is self-report of attention, not a substitute for the click log.**
  Where the two disagree, trust the log and treat the disagreement itself as
  a finding worth a line in Part 7.
- **This is a convenience panel using a seeded demo catalog**, not a
  representative sample or real search traffic — state that once in the deck,
  the same limit `wishlist-survey.md` already states for its own sample.

## Do not add

- Anything about price, discounts or a hypothetical sale — C‑1 bans it in the
  product, and asking about it here invites an answer nobody can act on.
- A second "would you use this" question. Q3, Q6, Q7 and Q14 already ask the
  same thing behaviourally, which is the only way this project asks it.
- A NPS-style 0–10 recommend score. It answers a marketing question this case
  study isn't grading and would cost a page for no line in Part 6 or Part 7.
